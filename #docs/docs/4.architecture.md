# 4. Architecture

## 4.1 Architectural goals

- Deliver a working end-to-end MVP quickly.
- Keep the app usable without model credentials.
- Isolate model-provider code from product logic.
- Make AI output reviewable and testable.
- Keep storage simple for local development.
- Avoid coupling the UI to a particular model's response format.

## 4.5 Core workflow

1. Frontend validates basic file type and size for quick feedback.
2. Backend independently validates upload size, MIME type, and actual image decoding.
3. Upload service stores the image using a generated identifier and safe filename.
4. Analysis service calls the selected provider adapter.
5. Provider returns raw output; adapter maps it into the internal schema.
6. Schema validation rejects malformed or incomplete output.
7. Frontend presents observations and inferences separately.
8. User edits the draft and explicitly confirms it.
9. Report service persists the report and its status history.
10. Dashboard reads persisted reports through the API.

## 4.6 AI provider interface

Define a provider interface such as:

```python
from typing import Protocol
from pathlib import Path
from app.schemas.analysis import AnalysisDraft

class VisionProvider(Protocol):
    async def analyze_image(self, image_path: Path) -> AnalysisDraft:
        ...
```

Implement:
- `MockVisionProvider`: deterministic local output for tests and demo mode.
- `MetaVisionProvider`: actual integration only after verifying the current official API, supported model, account permissions, and request schema.
- Other providers only if deliberately approved and documented.

The product layer must not know provider-specific response shapes. Do not assume Muse Spark, Muse Image, or SAM 3.1 is accessible through a particular endpoint until verified against current official documentation and the participant account.

## 4.7 Internal analysis schema

Example shape:

```json
{
  "category": "blocked_drain",
  "title": "Possible obstruction in roadside drain",
  "observations": [
    "Visible debris appears to cover part of the drainage channel."
  ],
  "inferences": [
    "The obstruction may reduce water flow; this cannot be confirmed from the image alone."
  ],
  "priority": "medium",
  "priority_reason": "The visible obstruction may affect drainage. A person should verify the site.",
  "uncertainties": [
    "Water flow and drain depth are not established by this photo."
  ],
  "provider": "mock",
  "model": "demo-v1"
}
```

This is an illustrative schema example, not actual model output. Mock results must be visibly labeled.

## 4.8 Data storage

MVP:
- SQLite for report metadata and status history.
- Local uploads directory for image files.
- Generated opaque identifiers for stored files.
- Store only the relative/internal file reference in the database.

Production considerations:
- Private object storage
- Authentication and authorization
- Retention/deletion policies
- Database migrations and backups
- Rate limits and monitoring

## 4.9 API contracts

### `GET /api/v1/health`
Returns service health and app version; must not reveal secrets.

### `POST /api/v1/analyze`
Accepts one image and optional context. Returns a validated draft, not a saved report.

### `POST /api/v1/reports`
Accepts a user-reviewed report draft and persists it.

### `GET /api/v1/reports`
Returns reports with optional filters such as category and status.

### `GET /api/v1/reports/{report_id}`
Returns one report or a safe `404`.

### `PATCH /api/v1/reports/{report_id}/status`
Validates the status transition and appends a status-history entry.

## 4.10 Status lifecycle

```text
draft → submitted → under_review → in_progress → resolved
                    └──────────────────────────→ rejected
```

Only allowed transitions should be accepted. For the single-user local MVP, the actor can be `local_user`; future multi-user authorization must be implemented before production use.

## 4.11 Deployment and configuration

Local development is the default. The application should run without external model access using the mock provider.

Before using a real provider:
1. Verify account access and model availability.
2. Read current official API documentation and terms.
3. Check rate limits, quotas, cost, and image restrictions.
4. Configure credentials only on the backend.
5. Add a timeout and safe error handling.
6. Add tests using mocked HTTP responses.
