# 5. Security and Privacy

## 5.1 Security goals

Protect uploaded images, prevent unsafe file handling, keep credentials private, limit data collection, and avoid presenting unverified AI output as fact.

## 5.2 Image upload safety

- Allow only explicitly supported formats: JPEG, PNG, and WebP.
- Enforce a configurable maximum size (initial target: 8 MB).
- Validate the extension, declared MIME type, decoded image format, and dimensions.
- Do not trust the client-provided filename.
- Generate random server-side filenames and store outside the frontend's public directory.
- Reject corrupt images and decompression-bomb-like dimensions.
- Never execute or serve uploaded content as HTML or JavaScript.
- Consider stripping EXIF metadata when storing a processed copy; do not expose embedded GPS metadata unintentionally.

## 5.3 Secrets and configuration

- Store provider keys in backend environment variables or a secret manager.
- Commit only `.env.example` with empty or placeholder values.
- Never place API keys in React source, browser storage, screenshots, logs, or public issue reports.
- Rotate a key immediately if exposed.
- Do not print complete environment configuration in diagnostic endpoints.

## 5.4 Privacy by design

- Ask only for information required to create the report.
- Make location optional and manually entered in the MVP.
- Explain what happens to uploaded images.
- Do not collect background location.
- Avoid retaining images longer than necessary.
- Provide a deletion workflow before inviting real users.
- Do not use images to identify people.
- Warn users not to upload unnecessary personal documents or close-up images of bystanders.

## 5.5 AI-specific safeguards

- Treat image content and model output as untrusted input.
- Do not follow instructions embedded in an image or metadata.
- Require schema validation for model output.
- Separate observations from inferences.
- Include uncertainty when the image does not support a conclusion.
- Require user review before a report is submitted.
- Do not generate allegations about named people or infer criminality.
- Do not claim a government body has received, validated, or resolved a report without verified integration.
- Do not make precise engineering or safety conclusions from a single image.

## 5.6 API security

- Set upload and request timeouts.
- Configure CORS to explicit frontend origins outside local development.
- Add rate limiting before public deployment.
- Validate all query parameters, body fields, identifiers, and status transitions.
- Return safe error messages; keep stack traces in restricted development logs only.
- Do not expose arbitrary filesystem paths through API responses.
- Use authentication and authorization before multi-user or public production deployment.
- Use HTTPS for deployed environments.

## 5.7 Storage and logs

- Exclude uploads, `.env`, SQLite databases, and user data from Git.
- Log request IDs and safe error categories, not API keys or full image contents.
- Avoid storing raw model prompts if they contain sensitive context.
- Set a documented local data retention policy.
- Keep backups protected if real user data is introduced.

## 5.8 Threat model

| Threat | Mitigation |
|---|---|
| Malicious or malformed upload | Decode and validate server-side; limit size and dimensions |
| API key exposure | Backend-only secrets; Git ignore; rotation procedure |
| Prompt injection in image/context | Treat content as data; constrain outputs to schema |
| False or hallucinated report | Human review; uncertainty; editable fields |
| Private location leakage | Optional manual location; careful logging and access controls |
| Unauthorized status changes | Validate transitions; add authentication before public use |
| Resource exhaustion | Upload limits, timeouts, rate limits, bounded retries |

## 5.9 Release checklist

- [ ] No secrets in Git history or frontend bundle.
- [ ] Unsupported and oversized uploads rejected.
- [ ] Upload filenames are generated server-side.
- [ ] Error responses reveal no stack traces.
- [ ] CORS is restricted for deployment.
- [ ] Mock mode is clearly identified.
- [ ] User confirms AI-generated reports before submission.
- [ ] Privacy and image-retention behavior is documented.
- [ ] Public deployment has authentication, rate limits, and deletion controls appropriate to its use.
