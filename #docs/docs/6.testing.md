# 6. Testing Strategy

## 6.1 Objectives

Prove that the core photo-to-report workflow is reliable, invalid inputs fail safely, AI output is validated, and the UI remains understandable during loading and failure.

## 6.2 Test layers

### Unit tests
Backend:
- Upload validation
- Analysis schema validation
- Category and priority normalization
- Status transition rules
- Report service behavior
- Mock provider determinism

Frontend:
- Priority and status labels
- Upload validation feedback
- Observation versus inference display
- Form validation
- Loading and error components

### Integration tests
- `POST /analyze` with valid image returns a valid draft.
- Unsupported/corrupt/oversized files return safe errors.
- `POST /reports` persists a reviewed report.
- `GET /reports` and `GET /reports/{id}` return saved data.
- Invalid status transitions are rejected.
- Provider timeout or malformed output does not crash the API.

### End-to-end tests
- Open app.
- Upload sample image.
- Run mock analysis.
- Edit title and location.
- Confirm and save report.
- Find report on dashboard.
- Update status.
- Refresh and verify persistence.

## 6.3 Test tools

Suggested:
- Backend: `pytest`, FastAPI `TestClient` or `httpx`
- Frontend: `vitest`, `@testing-library/react`, `@testing-library/user-event`
- Optional browser E2E: Playwright

Use dependency versions compatible with the installed Python and Node versions.

## 6.4 Required test cases

| Area | Case | Expected result |
|---|---|---|
| Upload | Valid JPEG | Accepted |
| Upload | Unsupported file | Rejected with helpful message |
| Upload | File above size limit | Rejected |
| Upload | Corrupt image | Rejected safely |
| Analysis | Mock provider | Deterministic schema-valid draft |
| Analysis | Missing provider key | Clear unavailable/configuration result |
| Analysis | Provider timeout | Recoverable error; no fake success |
| Output | Unknown category | Normalized to `unknown` or rejected by schema |
| Review | User edits draft | Edited values are what gets saved |
| Reports | Unknown report ID | `404` response |
| Status | Invalid transition | `422` or documented conflict response |
| UI | No reports | Helpful empty state |
| UI | API failure | Error and retry option |
| Privacy | EXIF metadata | Not exposed unintentionally |
| Security | Oversized upload | Rejected before expensive analysis |

## 6.5 Mocking external AI

Tests must not require paid API access or network access. Inject a provider interface and use a deterministic mock. Test the real provider adapter separately with mocked HTTP responses. Any live smoke test must be opt-in and must not run in normal CI.

## 6.6 Sample test data

Keep small, non-sensitive sample images in a dedicated test-fixtures directory only when licensing permits. Do not commit personal photographs or images containing identifiable bystanders without permission.

Create examples for:
- Clear pothole
- Visible debris in a drain
- Accumulated waste
- Ambiguous or low-quality image
- Image unrelated to infrastructure

For unrelated or unclear images, the system should return `unknown` or ask for clarification rather than inventing an issue.

## 6.7 Commands (planned)

Backend:
```powershell
cd backend
pytest -q
```

Frontend:
```powershell
cd frontend
npm test
```

If the frontend test script is not configured yet, add it to `package.json` as part of implementation rather than assuming it exists.

## 6.8 Quality gates

Before each milestone:
- All relevant automated tests pass.
- No console errors in the primary workflow.
- Manual smoke test on desktop and a narrow mobile viewport.
- Error and empty states checked.
- `git diff` reviewed.
- No secrets or generated user data added to the commit.

## 6.9 Definition of done

A feature is done when it works in the UI, has appropriate validation and failure handling, includes tests for its core behavior, follows the security requirements, and is documented where setup or behavior is not obvious.
