# 1. Product Requirements Document (PRD)

## 1.1 Product summary

CivicLens AI is a human-reviewed visual reporting tool for visible community infrastructure problems. It converts a user-submitted photograph into an editable draft report and allows the user to track the report's status.

## 1.2 Problem statement

Residents may notice a pothole, blocked drainage channel, waste pile, or damaged public asset but lack a consistent way to describe and track the issue. A photograph alone may lack category, context, location, and follow-up status. CivicLens structures this information without claiming to replace local authorities or field inspection.

## 1.3 Target users

- Residents who want to document a local issue
- Community organizers who maintain a list of issues
- Volunteers or moderators who review reports
- Hackathon judges evaluating an end-to-end AI workflow

## 1.4 Goals

1. Turn a photo into an editable structured report.
2. Make AI observations understandable and reviewable.
3. Preserve the original photo and user corrections in a report record.
4. Support a small dashboard and a transparent status lifecycle.
5. Demonstrate a useful multimodal workflow with a fallback when model access is unavailable.

## 1.5 Non-goals

- Replacing emergency services or government reporting portals
- Automatically proving that an issue exists at a precise location
- Automatically assigning blame or responsibility
- Inferring identity or sensitive traits of people in a photo
- Promising that an authority received or resolved a report
- Performing unvalidated engineering measurements from ordinary photos

## 1.6 Primary user journey

1. User opens the app and chooses **Create report**.
2. User uploads a supported image.
3. User optionally enters community, street, landmark, or coordinates manually.
4. User requests analysis.
5. The app shows a draft category, observations, possible concerns, and suggested priority.
6. The UI distinguishes image-visible observations from AI inferences and labels uncertainty.
7. User edits fields, confirms the photo and location, and saves the report.
8. User views the report on the dashboard and updates its status as permitted.

## 1.7 MVP features

### P0 — required
- Responsive landing/dashboard
- JPG, JPEG, PNG, and WebP upload
- File-size and file-type validation on frontend and backend
- Preview image before analysis
- Manual location fields; location is optional
- Analysis service interface with deterministic mock provider
- Structured report draft
- Edit-before-save workflow
- Report list, detail view, filters, and status updates
- Clear mock-mode banner when no real AI provider is configured
- Useful loading, empty, error, and retry states
- Local setup documentation

### P1 — desirable
- Vision-model adapter configured through environment variables
- Evidence/uncertainty panel
- Optional segmentation overlay through an adapter
- Export report as JSON or printable page
- Duplicate-warning heuristic based on category, time, and manually supplied area

### P2 — later
- User accounts and roles
- Map visualization
- Notifications
- Agency integrations
- Moderation queue and multi-user workflows

## 1.8 Report data model

A report should include:

- `id`: generated opaque identifier
- `created_at`, `updated_at`: ISO 8601 timestamps
- `status`: controlled status enum
- `category`: `pothole`, `blocked_drain`, `waste`, `damaged_infrastructure`, `other`, `unknown`
- `title`: short editable summary
- `description`: human-readable report
- `observations`: list of statements directly supported by visible image content
- `inferences`: separate list of cautious model-generated possibilities
- `priority`: `low`, `medium`, `high`, `unknown`
- `priority_reason`: short explanation; never a bare unexplained score
- `confidence`: optional model confidence only if the provider meaningfully supplies it; otherwise omit
- `location_text`: optional user-entered location
- `image_path`: internal storage reference, not a public filesystem path
- `analysis_provider`, `analysis_model`: provenance metadata when available
- `reviewed_by_user`: boolean
- `status_history`: timestamped changes with actor label where available

Never fabricate a GPS coordinate, confidence value, model provenance, or report status.

## 1.9 Priority guidance

Priority is a suggestion, not a verified risk assessment.

- **High:** visible condition plausibly creates immediate access or safety concerns; explain why and recommend appropriate human review.
- **Medium:** visible issue may disrupt access or normal use but no immediate danger is established.
- **Low:** visible maintenance issue without an obvious immediate hazard.
- **Unknown:** insufficient visual context.

The app must not call an issue an emergency based only on model output. Provide a neutral instruction to contact appropriate local services if the user believes there is immediate danger.

## 1.10 Success metrics for the demo

- User can complete photo-to-saved-report workflow without developer tools.
- Invalid uploads are rejected with clear errors.
- A reviewer can tell mock analysis from real model output.
- Every AI draft can be edited before saving.
- Report state survives backend restart when SQLite is enabled.
- Automated tests cover validation, report creation, and status transitions.
- Demo includes at least three distinct issue examples and one uncertain/ambiguous image.

## 1.11 Acceptance criteria

- Upload rejects unsupported types and files larger than configured maximum.
- Analysis returns a schema-valid draft or a recoverable error.
- The UI labels visible observations separately from inferred explanations.
- No report can be submitted through the main flow without user confirmation.
- Status changes follow the allowed lifecycle.
- Empty and error states do not crash the app.
- No secrets are required for mock mode.
- Real model integrations fail safely if credentials are absent or the provider is unavailable.

## 1.12 Risks and mitigations

| Risk | Mitigation |
|---|---|
| Hallucinated analysis | Structured output, uncertainty labels, user review, tests |
| API access unavailable | Mock provider and adapter design |
| Poor or misleading image | Allow `unknown`; request another image |
| Sensitive data in photos | Warn users; minimize retention; avoid face identification |
| Scope too large | Finish photo-to-report workflow before maps, accounts, or integrations |
| False claims of official action | Use explicit statuses and no fake agency integrations |

## 1.13 Release definition

MVP is ready when a new developer can install dependencies, run frontend and backend locally, upload a sample photo, review a clearly labeled analysis draft, save a report, and update its status using documented commands.
