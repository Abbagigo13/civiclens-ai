# 3. Code Style and Engineering Conventions

## 3.1 General rules

- Prefer readable, explicit code over clever abstractions.
- Keep components and functions small enough to understand quickly.
- Use descriptive names and consistent domain terminology.
- Avoid duplicating business rules across frontend and backend.
- Validate all untrusted input on the backend, even when frontend validation exists.
- Do not commit generated builds, virtual environments, databases containing user data, uploads, or secrets.

## 3.2 Frontend

Preferred: React + Vite + TypeScript.

- Components: PascalCase, e.g. `ReportCard.tsx`.
- Hooks: `use` prefix, e.g. `useReports.ts`.
- Utilities: camelCase, e.g. `formatTimestamp.ts`.
- Keep feature code in `src/features/<feature>/`.
- Keep reusable UI in `src/components/`.
- Keep API access in `src/lib/api/`; do not scatter raw `fetch` calls across components.
- Use `async/await` and handle loading, success, empty, and error states.
- Use typed API response models.
- Avoid `any`; if unavoidable, explain it and narrow the type quickly.
- Never put API secrets in `VITE_*` variables; frontend environment variables are public.

## 3.3 Backend

Preferred: Python + FastAPI + Pydantic.

- Use 4 spaces for indentation.
- Use snake_case for variables, functions, and modules.
- Use PascalCase for classes.
- Add type annotations to public functions and service boundaries.
- Use Pydantic models for request and response validation.
- Keep routes thin; business logic belongs in services.
- Keep persistence in repositories.
- Use explicit exception handling and meaningful HTTP status codes.
- Do not return stack traces or secrets to clients.
- Avoid blocking network calls inside async routes; use an appropriate async client or a normal synchronous route.

## 3.4 API conventions

- Base prefix: `/api/v1`.
- JSON responses use consistent snake_case fields.
- Use ISO 8601 timestamps with timezone information.
- Return structured errors with a stable code and safe user-facing message.
- Pagination should be added before report volume becomes large.
- Document endpoints in FastAPI OpenAPI docs.

Initial endpoints:
- `GET /api/v1/health`
- `POST /api/v1/analyze`
- `POST /api/v1/reports`
- `GET /api/v1/reports`
- `GET /api/v1/reports/{report_id}`
- `PATCH /api/v1/reports/{report_id}/status`

## 3.5 Git conventions

Use small, purposeful commits:
- `feat: add image upload validation`
- `feat: add report review form`
- `fix: handle unavailable analysis provider`
- `test: cover report status transitions`
- `docs: clarify local setup`

Do not include unrelated changes in one commit. Never commit `.env`, API keys, tokens, or personal photos.

## 3.6 Error handling

- Tell the user what happened and what they can do next.
- Log diagnostic details server-side without logging secrets or unnecessary personal data.
- Treat AI timeouts and invalid model output as recoverable failures.
- Validate model output against a schema before returning it.
- If the model output is invalid, retry at most a small configured number of times or return a safe error; never silently fabricate a result.

## 3.7 Dependencies

- Add dependencies only when needed.
- Prefer maintained packages with clear licenses and reasonable transitive dependencies.
- Pin or lock dependency versions for reproducible installs.
- Record model/API requirements and limitations in documentation.
- Do not assume a service is free or accessible until verified.
